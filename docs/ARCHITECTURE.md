# 架构与所有权

自建 Git `git.cflmy.cn/cflmy` 是代码、工单和合并的权威，`ci.cflmy.cn` 是 CI 权威。GitHub 作为镜像或分发渠道。生态主仓库以直接 Git submodule 固定组件提交，`stdlib/`、`extensions/`、`tools/` 是分类目录。

| 层 | 所有权 |
| --- | --- |
| CLI | Markdown 映射、AST/IR、Runtime、Value、权限/隔离/预算及 Package、Plugin、Provider、Foreign、Tool、Analysis、Observation 公共契约 |
| 标准库 | 基础安装默认提供的通用低层函数，以及对受控宿主原语的薄封装 |
| 扩展 | 可选算法、领域协议与独立后端。`marqdo-ext-<领域>` 按独立依赖、安全或发行边界命名 |
| Tool | 通过公共 CLI 接口处理文档及制品的独立工具，例如静态知识、证明、观察和质量诊断 |
| 应用 | 具体用户任务和业务流程，例如 qdagent |
| 生态主仓库 | 组件关系、精确组合、跨组件验收、发行与责任治理 |

CLI 编译只需其自身实现。完整基础发行由 CLI、必需 Worker 和统一标准库 Bundle 构成。标准库组件只依赖 CLI 公共语义和更低层标准库，扩展可以依赖标准库与明确声明的其他扩展。Tools 使用公开协议与自身依赖，各工具的数据格式互操作须由产生者明确发布契约。组件依据各自发版制品独立构建，不依赖主仓库源码。

组件的职责、阶段和依赖只在 [components.toml](../components.toml) 维护。子模块远端在 `.gitmodules`，提交在 Git tree，程序依赖仍在现行包清单及锁。`requires` 描述直接构建与制品依赖，`checks_with` 描述协同验收。计划中的依赖在真实接入前以 imports、构建输入和制品核实。依赖图必须无环。

## 新增能力与公共边界

先复用职责匹配的组件。需要独立维护、依赖、安全或发行边界时，为新仓库发起评审。加入标准库须证明基础发行默认需要、至少三个领域真实复用、依赖闭包受控，并说明错误、授权和预算语义。

需要新增 builtin、HostOp、值类型、语法或公共协议字段时，在 CLI 提交 ADR，写明现有机制为何不足、最小复现、三个领域用例、替换及正负例。公开接口破坏性更新按同一候选组合切换产生者和消费者，保留单套现行协议。历史行为通过固定版本的历史发行复现。

跨组件测试以真实 CLI/Worker、独立消费者和现行权限配置验证。Native 后端与外部工具按 CLI 安全边界执行，权限、隔离和预算声明以可验证的实际行为为准。
