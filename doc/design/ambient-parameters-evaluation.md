## 0. 结论：你的示例其实**不需要**隐式推断

先把一个关键事实摆出来：**你的例子里 `n=31` 明明写在那儿**。

```markdown
# main

对**n=31**执行**加一函数**
```

`n` 的绑定**就写在句子里**，这不是「从上下文推断」，这是**具名实参换了语序**。
所以这个写法需要的是**新的叙述式调用语法**，不是新的作用域语义。

它今天跑出来的结果很能说明问题：**无输出、无报错、退出码 0**。
不是参数推断失败，而是 `执行**加一函数**` 里的裸名字**只是被求值然后丢弃**，
从来没被当成一次调用。

三层拆解：

| 层 | 写法 | 需要什么 | 裁决 |
|----|------|---------|------|
| **L0 叙述式调用** | `对**n=31**执行**加一函数**` | 只要语法糖（绑定仍在句中） | ✅ **可做，且安全** |
| **L1 就近绑定** | 上一行 `**n=31**`，下一行 `执行**加一函数**` | 段落级隐式作用域 | ⚠️ 能做但危险，不建议 |
| **L2 真隐式** | 只写 `执行**加一函数**`，n 全靠上下文 | 动态作用域 | ❌ **不建议**，见 §4 |

## 1. 实测：今天到底发生了什么

| # | 用例 | 实测 | 说明 |
|---|------|------|------|
| 1 | 你的示例原样 | **无输出、无报错、exit 0** | 静默 no-op |
| 2 | 同样写法 + `> print text=`n`` | `main里的n=31` | **散文行里的 `**n=31**` 真的执行了** |
| 3 | 只写 `对`加一函数`执行` | `done`，无报错 | 裸名字只被求值丢弃，**未调用** |
| 4 | `**n = 31**` + `> 加一函数`（不传参） | `missing argument for parameter n` | **函数看不见调用者的 `n`** |
| 5 | `> 加一函数 n=31` | `32` | 显式写法今天就能做 |
| 6 | `# main` 读 frontmatter `税率` | `0.1` ✅ | 入口可见 |
| 7 | `## 函数` 读同一个 `税率` | `undefined variable` ❌ | 函数不可见 |
| 8 | 浏览器 WASM 入口调用函数 | metadata + `entry_bindings` **都会传** | 见 §5，**与 CLI 不一致** |

**第 2 与第 3 条合起来是关键**：散文行里的粗体确实会执行，但一个裸函数名在粗体里
只是一个**表达式语句**（值算了就丢），不会变成调用。所以「看起来该调用」的句子，
实际什么也没做——又是一次静默失败（与 D9 同一类）。

**第 4 条是语义基石**：Marqdo 现在的作用域是**严格分离**的，
函数只能看到自己的形参与局部变量。你想要的 L2，就要拆掉这块基石。

## 2. 你自己的担心是对的：数据在这里

你提到「大项目变量名会难以使用」。我把仓库里 `lib/ ext/ examples/ tests/` 全扫了一遍：

| 指标 | 数值 |
|------|------|
| 扫描函数数 | **1322** |
| 不同形参名 | 819 |
| **被 ≥5 个函数共用的形参名** | **130 个** |

撞车最严重的一批：

| 形参名 | 用它的函数数 |
|--------|-------------|
| `path` | **70** |
| `value` | 59 |
| `text` | 53 |
| `id` | 47 |
| `list` | 38 |
| `内容` | 38 |
| `路径` | 35 |
| `a` / `b` | 各 32 |

结论很直接：**如果参数靠上下文推断，那么每次调用一个读 `text` 的函数，
它都会去捡当前作用域里的 `text` 是什么**。53 个函数在等这个值——
撞车是常态，不是例外。这不是「大项目才有」的问题，中型项目就已经不可控。

## 3. L0：叙述式调用（推荐做）

### 3.1 目标写法

```markdown
## 加一函数

对`n`我们让**n=n+1**之后返回*n*

# main

**结果 = 对 n=31 执行 加一函数**
> print text=`结果`        # → 32
```

### 3.2 语义映射（零模型改动）

```
对 <绑定子句> 执行 <函数名>   ≡   Call { callee: <函数名>, args: [<绑定子句>…] }
```

也就是**纯粹换语序**的语法糖。它与今天的

```markdown
**结果 = > 加一函数 n=31**
```

产出**同一个 `CallExpr`**。因此：

| 面 | 影响 |
|----|------|
| 契约校验（T2.1/T2.2） | **不变**（实参照常绑定与校验） |
| EKC 指纹 `collect_calls` | **不变**（callee 仍是静态名） |
| 字节码 `Op::Call(fid, argc)` | **不变** |
| 序列化 / 沙箱 | **不变** |
| `view` 渲染 | 需决定回显哪一种语序 |

这正是它与「一等函数」「动态作用域」的本质区别：**只改写法，不改调用模型。**

### 3.3 设计细节要定的三件事

1. **动词**：`执行` 目前**不是**关键字；而 `调用` **已经是**关键字（`src/aliases.rs:39`
   把 `调用` 映射到内建 `call_fn`）。两个近义词并存会混乱，需要二选一或明确分工。
2. **绑定子句的边界**：`对 n=31 执行 …` 里 `n=31` 到 `执行` 之间是参数区；
   多参数写 `对 n=31 m=2 执行 …`。
3. **与散文的冲突**：`对` 起头的行今天是叙述（CJK 开头 = 注释）。
   要让这行变成代码，得给「叙述里出现 `执行 <函数名>`」一个可判定的规则，
   否则又是一处「看起来是代码、实际是注释」的静默陷阱。

## 4. L2：真隐式参数（不建议）

### 4.1 它到底是什么

L2 = **动态作用域**（dynamic scoping）：被调函数在**调用者的环境**里查找自由变量。
历史上被反复试过、也反复放弃：早期 Lisp 改成词法作用域、Shell 的动态作用域被视为坑。

### 4.2 七条硬伤（每条都是具体后果，不是理论洁癖）

| # | 问题 | 具体后果 |
|---|------|---------|
| 1 | **同名捕获** | `加一函数` 调 `记录日志`，两者都读 `text` → 日志函数静默拿到加一的局部值，输出错内容而不报错 |
| 2 | **递归自毁** | `n=n+1` 后调自身：内层看到的是**已被改过的** n（还是副本？）——必须新增一套遮蔽规则，而规则本身又会成为新的坑 |
| 3 | **无法复用** | 同一函数两次不同入参，只能反复改外部变量并祈祷调用顺序，等于把「参数」退化成全局可变状态 |
| 4 | **契约报废** | `call_arg_diag` 在**调用边界**校验实参类型；如果不传实参，就没有校验点。T2.1/T2.2 契约体系直接失效 |
| 5 | **指纹/arity 失真** | `collect_calls` 记录被调名，arity 由形参推断；隐式调用在 AST 上看起来是零参调用 → 复用预检、`plan` 能力匹配、查重全都失真 |
| 6 | **沙箱与序列化** | `sandbox.run` 以隔离方式执行文档；隐式依赖外部作用域会破坏隔离语义；环境也必须可序列化 |
| 7 | **不可审计** | 函数行为依赖看不见的上下文——这就是「全局可变状态」的经典问题，与「文档即程序、可被人读懂」直接冲突 |

再叠加 §2 的数据（130 个名字被 ≥5 函数共用），第 1 条不是边角情况，而是默认情况。

### 4.3 但有一个**受限版**值得考虑

如果你真正想要的是「短脚本读起来顺」，那么下面这个版本是安全的：

> **常量默认值**：允许函数在**未传入**某形参时，从**文件级常量**取值。

```markdown
---
title: 报价
税率: 0.1
---

## 含税
    + `金额`

*`金额` * (`税率`)*     # 税率 未传入 → 取 frontmatter 常量

# main

**a = > 含税 金额=100**   # 10
**b = > 含税 金额=100 税率=0.06**  # 6，显式覆盖
```

为什么它安全而 L2 不安全：

| 维度 | L2 动态作用域 | 常量默认值 |
|------|--------------|-----------|
| 取值来源 | 调用者的**任意**变量 | 文件顶部**写一次**的常量 |
| 静态可判定 | ❌ 取决于运行路径 | ✅ 打开文件就能看到 |
| 随调用者变化 | ✅ 会变（最危险） | ❌ 不会 |
| 契约 | 失效 | 仍可校验（实参照常声明） |
| 序列化/沙箱 | 破坏隔离 | 可序列化（常量是数据） |
| 复用 | 破坏 | 不受影响 |

**关键差别**：常量是**文档的一部分**（frontmatter 就在文件开头，人读得到），
而动态作用域的值是**运行路径的一部分**（人读不到）。

## 5. 顺带发现的真问题：CLI 与 Web 的环境不一致

实测 §1 第 6/7/8 条时发现：

| 路径 | 函数可见环境 | 源码 |
|------|-------------|------|
| `# main`（CLI 运行） | frontmatter metadata ✅ | `src/interp.rs:473` `Env::with_metadata` |
| **普通函数调用** | 只有实参 ❌ | `eval_call` 用 `Env::new()` |
| **浏览器 WASM 入口** | metadata ✅ + `# main` 的 `entry_bindings` ✅ | `invoke_in_entry`（`src/interp.rs:365`） |

也就是说：**同一份文档，在浏览器里函数能读到 frontmatter 常量、还能读到 `# main`
的绑定；在 CLI 里读不到。** 行为随运行面不同而不同。

这是一个**真实缺陷**，已记入 [D11](../research/qdagent-refactor-defects-2026-10.md)：

- 对使用者：同一文件在 Web 能跑、在 CLI 报 `undefined variable`，极难排查
- 对设计：说明「受控环境通道」其实已经存在（只是没在 CLI 打开），
  这既是 L2 受限版的现成基础，也是必须先统一的地方

## 6. 建议

| 优先级 | 事项 | 性质 |
|--------|------|------|
| 1 | **先统一 CLI/Web 的函数环境**（D11） | 修缺陷，消除行为分裂 |
| 2 | **做 L0 叙述式调用**（`对 X 执行 F`） | 纯语法糖，零模型改动，554 回归可守 |
| 3 | 若要「少写参数」，做**常量默认值**（§4.3） | 受控隐式，静态可判定 |
| 4 | **不做 L2 动态作用域** | 七条硬伤 + 130 个撞车名 |

关于「代码即文档」的取向，我的理解是：

> 文档化的是**写法**（句子怎么读），不是**语义**（值从哪来）。
> 让句子更像人话是值得的；让值从看不见的地方来，是把可读性换成不可预测性。
