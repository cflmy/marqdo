## 0. 先接受纠正：错在哪

我上一轮提的 `对**n=31**执行**加一函数**`，靠**未标记的词「执行」**来触发调用。这确实违背底层原则：

> **叙述（未标记）= 默认安全，不执行；标记 = 才进编译器。**

一旦「执行」这种词能改变语义，那么：

- 作者改一句措辞（"执行" → "运行" / "调用" / 换个说法）就可能改变程序行为；
- 读者无法只看标记判断哪句是代码——必须逐字读叙述；
- 与 D9 同类的静默风险：语义藏在叙述里。

**所以本文的设计约束是硬的**：

> **调用的每一个语义成分（被调者、每个实参、绑定关系）必须落在标记内；
> 叙述词只能起连接与解释作用，永不改变语义。**

## 1. 先盘清「标记字母表」

要设计调用，先得知道手上只有哪些字。

| 标记 | 现行语义 | 可否参与构成调用 |
|------|---------|-----------------|
| `**…**` | 执行段（赋值 / 调用 / 表达式） | ✅ 主载体 |
| `*…*` | 返回 | ✅ 终止 |
| `` `x` `` | 变量引用；首次出现即声明 | ✅ 槽名 |
| `` `x` = `` | 叙述中的绑定 | ✅ 槽赋值 |
| `**x = …**` | 赋值 | ✅ |
| `> …`（行首） | 调用语句 | ✅ 已是调用标记 |
| `[callee] args` | 方括号调用（消歧 / 前置修饰） | ✅ 已是调用标记 |
| `[k](coll)` | 取元 | ⚠️ 与调用抢外形（已否） |
| `- [x](coll)` | 遍历 | — |
| `#` / `##` | 对象 / 函数声明 | — |
| 表格 | 数据 / 契约 | — |
| ```lang | 外联代码 | — |

**关键观察**：调用载体其实只有三种标记：`> 行`、`**…**`、`[callee]`。
而 `[k](coll)` 这个外形已被取元独占（前几轮结论），不能用。

所以问题收敛为：

> **在 `**…**` 或 `> …` 内部，用哪些标记把「函数名」和「槽赋值」连起来？**

## 2. 可读性从哪来（这是设计的核心）

Marqdo 的叙述与代码是**两层**：叙述解释「为什么」，标记表达「做什么」。
所以可读性不是靠把叙述词变成语法，而是靠：

1. **标记本身足够像自然记号**（`=`, `(`, `)`, `→` 都是跨语言的）；
2. **叙述与标记紧邻**，人一句一码地读；
3. **同一件事只写一遍**（叙述不要复述代码）。

一句话：

> **叙述负责「说人话」，标记负责「说准话」；两者相邻即高可读，混在一起即两败。**

## 3. 三个候选设计

### 设计 A — 括注具名调用：`**加一函数(n=31)**`

**读法**：`加一函数(n=31)` —— 与数学/几乎所有语言的函数调用同构。

```markdown
## 加一函数

对 `n` 让 **n = n + 1**，返回 *n*

# main

**结果 = 加一函数(n=31)**
```

| 维度 | 评价 |
|------|------|
| 完全由标记构成 | ✅ 整段在 `**…**` 内 |
| 无歧义 | ✅ 圆括号紧跟名字 = 调用；取元需方括号，不冲突 |
| 与叙述结合 | ✅「把 n 设为 31 后**加一函数(n=31)**」 |
| 多参数 | ✅ `f(a=1 b=2)` |
| 编译器 | ✅ 具名 → 编译期映射到槽下标（见 §4） |
| 实现成本 | ⚠️ 需改参数分词器：`)` 作终止符、逗号、嵌套（原型已验 554/0，但 `f(1 2)` 的末参数会吞 `)`） |

### 设计 B — 箭头槽赋值：`**n=31 → 加一函数**`

**读法**：「n 设为 31，交给加一函数」——最贴合汉语「先条件、后动作」语序。

```markdown
# main

**n=31 → 加一函数**
```

| 维度 | 评价 |
|------|------|
| 完全由标记构成 | ✅ `→` 是符号标记，不是词 |
| 可读性 | ✅✅ 流水线极顺：`**订单 → 计税 → 汇总**` |
| 无歧义 | ⚠️ 需定义优先级；`**x = a=1 → f**` 有歧义，得靠括号 |
| 求值结果 | ⚠️ 箭头式天然是语句式；要拿返回值还得包一层 |
| 实现成本 | 中：新增运算符 + 优先级 + 与 `=`/`*…*` 的交互 |

### 设计 C — 现成空格式：`**加一函数 n=31**`（今天就可用）

| 维度 | 评价 |
|------|------|
| 完全由标记构成 | ✅ |
| 实现成本 | **零**（实测 `**r = 加 1 2**` 已可跑） |
| 可读性 | ⚠️ 参数边界靠空格；函数名含空格时不可用（D8） |
| 编译器 | ✅ 具名同样可映射槽位 |

### 三者的取舍

| | A 括注 | B 箭头 | C 空格 |
|---|---|---|---|
| 像通用函数调用 | ✅✅ | ⚠️ | ✅ |
| 中文语序自然 | ⚠️ | ✅✅ | ✅ |
| 参数边界清晰 | ✅✅ | ✅ | ❌（空格切分） |
| 链式组合 | ⚠️ | ✅✅ | ❌ |
| 改动成本 | 中 | 中高 | **零** |
| 与取元冲突 | 无 | 无 | 无 |

## 4. 「不分实参形参」：编译器视角的真实收益

你问的是：不再区分实参/形参，是否意味着变量总在某个固定位置、能否减少 IO。
这一节用实测回答，结论会有点意外。

### 4.1 现状：两条执行路径，差异 3.8 倍

| 路径 | 参数如何绑定 | 200k 次调用（1 个 int 实参） | 2000 次调用（500 元素列表） |
|------|-------------|------------------------------|------------------------------|
| **树遍历**（默认 `Backend::Tree`） | `Env { HashMap<String, Value> }`，每个实参 `k.clone()` + `v.clone()`（**深拷贝**） | 167 ms | 66 ms |
| **字节码**（`--backend bytecode`） | `slots: Vec<Value>`，`pop` 后**按位置移动**入槽（**无克隆、无哈希**） | **44 ms** | **23 ms** |

源码依据：

```rust
// src/bytecode/vm.rs  Op::Call(fid, argc)
let mut slots = vec![Value::None; callee.locals.len().max(argc).max(1)];
for i in (0..argc).rev() {
    slots[i] = pop(&mut stack)?;        // 移动，不克隆
}
frames.push(Frame { fn_idx: fid, ip: 0, slots, .. });
```

### 4.2 三个结论

**结论一：「变量始终在某个位置」已经是字节码的现实。**
形参按下标落槽，实参按位置移动入槽。这正是你说的模型——它已经存在。

**结论二：收益是真的，3.8×。**
每次调用 0.83µs → 0.22µs；大实参 33µs → 11.5µs（省掉了深拷贝）。

**结论三（关键）：这与「不分实参形参」的语法无关。**
槽位化只需要「编译期知道形参顺序」，而形参顺序今天就有（v0.3 体推断给出确定顺序）。
真正的瓶颈是**树遍历解释器用名字哈希 + 深拷贝**，以及**默认后端是 Tree**。

> **所以：不要用性能去论证语义变更。**
> 想省 IO，把默认后端切到字节码、或把树遍历解释器槽位化即可——
> 这是一条与语法正交的工程路径，收益确定、风险可控。
> 而改语义（动态作用域）换来的性能，等于用正确性买速度。

### 4.3 但有一个真实的语法—性能耦合点：具名 vs 位置

这是本节最有价值的发现。**在「形参由体推断」的世界里，形参顺序 = 叙述里首次声明的顺序**
（v0.3 §8.2：顺序按升参名字的首次声明事件出现序）。而叙述是可以自由改写的。

我用两个只差一句话序的文件做了实验：

```markdown
## 减
对于`a`和`b`。        ← 叙述顺序 a, b
*`a` - `b`*
```

```markdown
## 减
对于`b`和`a`。        ← 只把叙述顺序改成 b, a
*`b` - `a`*
```

| 调用写法 | 叙述 a 在前 | 叙述 b 在前 |
|---------|------------|------------|
| 具名 `a=10 b=3` | 7 | -7（语义随函数体改变，符合预期） |
| **位置 `10 3`** | 7（a=10,b=3） | **7（b=10,a=3）** ← **绑定翻转了** |

**同一行调用代码 `> 减 10 3`，只因为作者改了前面的叙述语序，实际绑定就变了，而且不报错。**

这在「实参形参不分」的模型下是致命的：既然只有槽、槽序来自叙述，
那么**位置传参等于把程序语义挂在叙述的可改写顺序上**。

**推论**：调用应当**以具名为准**，位置实参在体推断世界里是脆弱语法。
这一点与编译器优化正好同向——具名调用让编译期把 `n` 静态映射到 `slots[0]`，
既稳又快（不需要运行期哈希，也不需要猜顺序）。

## 5. 我的设计建议

### 5.1 主形态：括注具名调用

```markdown
## 加一函数

对 `n` 让 **n = n + 1**，返回 *n*

# main

**结果 = 加一函数(n=31)**
```

理由：

1. **全部语义在标记内**（满足你的核心原则）；
2. 与通用函数调用同构，零学习成本；
3. 具名 → 编译期静态映射槽位（对接字节码已有的 `slots[]`）；
4. 不碰取元 `[k](coll)`，不碰遍历 `- [x](c)`；
5. 参数边界显式，顺带解决函数名含空格的调用难题（D8）。

### 5.2 位置实参：降级而非禁止

| 情形 | 建议 |
|------|------|
| 单参数 | 允许 `f(31)`（无歧义、写法自然） |
| 多参数 | **要求具名**；位置仅保留给 `> f 1 2` 这种旧写法，并在 `check` 里 **warn** |
| 理由 | §4.3：顺序来自叙述，可被改写而不报错 |

### 5.3 箭头（设计 B）作为可选补充

如果后续确实需要「流水线可读性」，再引入 `→`，定位为**语句式组合子**：

```markdown
**订单 → 计税 → 汇总**
```

但它是增量特性，不是本设计的前提。优势是链式，代价是优先级与返回值语义。

### 5.4 明确不做

| 方案 | 理由 |
|------|------|
| 未标记动词触发调用（上轮 L0） | 违背「叙述默认安全」 |
| `[f](args)` | 与取元同形，已实测 2 个真实冲突文件 |
| 动态作用域（参数从上下文推断） | 七条硬伤 + 130 个撞车形参名 |
| 位置实参作为主流 | §4.3 叙述顺序会静默改变绑定 |
