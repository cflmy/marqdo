---

## 0. 一句话

> **警告的作用域 = 模型自己刚改的那几行；投递次数 = 一次；附着在造成它的那次编辑的返回里。**

不是"我们让它少报"，而是**同一件事在结构上不可能被报第二次**。

---

## 1. 机制为什么成立：前后两版本来就在手里

看现有 `repair_apply`（`src/mlsp.rs:233`）的实现：

```rust
let source = source_text(params)?;          // ← 改动前（before）
...
match crate::repair::apply_edits(&source, &ranges, &edits) {
    Ok(new_source) => {                     // ← 改动后（after）
        Ok(json!({"source": new_source, "edits_applied": edits.len()}))
    }
    ...
}
```

**`source` 和 `new_source` 在同一个函数作用域里同时存在。**
所以"比较改动前后"不需要任何外部东西：

| 需要的东西 | 从哪来 |
|-----------|--------|
| 改动前的 AST | `parse(source)` |
| 改动后的 AST | `parse(new_source)` |
| 标签配对 | 两份 AST 里的标签节点（按标签文本 + 序号） |
| `()` 是否变了 | 比较两边的 AST 指纹 |
| `[]` 是否变了 | 比较标签文本 |

**零 git、零台账、零缓存文件、零环境依赖。** 这就是"agent 回路根本不需要 VCS"的含义。

### 1.1 指纹怎么做（T1 只需要「进程内一致」）

这一点让实现变得很轻：

- `Expr` 目前 `#[derive(Debug, Clone)]`，**没有 `PartialEq`**（`src/ast.rs:184`）。
- 但 T1 只在**同一个进程内**比较前后两版，**不需要跨版本、跨机器稳定的指纹格式**。
  于是最简做法是：把 `()` 的比较键取为 `format!("{:?}", expr)`——同一次运行内确定即可。
- 若想更严谨，可给 `Expr` 及其成员补 `#[derive(PartialEq)]`（纯机械改动；`Literal` 含 `f64`，
  只可 `PartialEq` 不可 `Eq`），然后直接结构比较，不产生字符串。
- 反过来，**T2/T3 才需要稳定指纹**（跨会话要能对上），那时才动用
  `knowledge/fingerprint.rs` 那套。

> 也就是说：T1 的实现成本 ≈ "解析两次 + 比较两棵子树"，没有版本化指纹的负担。

## 2. 一次修复轮次的完整时序

```
第 N 轮
 ┌─ validate        → 语法/契约诊断（不含标签扫描）
 ├─ repair_targets  → 靶点 + 允许范围
 ├─ 模型产出 edits  （例如：把 `* 金额` 改成 `/ 金额`）
 └─ repair_apply(source, ranges, edits)
        │
        ├─ before = source
        ├─ after  = apply_edits(...)
        ├─ 解析两版 → 比较每个标签的 () 指纹
        └─ 返回：
             { "source": after,
               "edits_applied": 1,
               "labels": { "stale": [ {标签, code_past, code_now, span} ] } }
```

模型在自己这次编辑的**响应里**看到：

```json
{
  "labels": {
    "stale": [{
      "text": "按 `税率` 计算总价",
      "code_past": "at(税率表, 档位) * 金额",
      "code_now":  "at(税率表, 档位) / 金额",
      "span": {"line": 42, "col": 12}
    }]
  }
}
```

它只需要回答一个问题：**"你刚才动了这段实现，描述还成立吗？"**

## 3. 为什么「重复」在结构上消失了

三个性质，缺一不可：

| 性质 | 内容 | 效果 |
|------|------|------|
| **作用域 = 自己的 diff** | 只看这次 `apply` 触及的标签 | 全仓库/全文件的旧债永远不进模型的上下文 |
| **投递 = 一次** | 只在造成它的那次响应里出现 | 不会在后续 `validate` 里重复出现 |
| **自包含** | 下一轮的 diff 是新的 | 模型不改那处 → 那条标签不再出现 |

**注意第三条的含义（也是代价）**：模型若忽略了提示，它**不会**在下一轮被再提醒——
因为它没碰那处。这是刻意的取舍：**宁可漏一次，也不反复骚扰**。

> 对比扫描式：一个 20 处标签的文件，5 轮修复里模型可能累计看到上百条重复提示；
> T1 下最多看到 **自己这几行涉及的 0–2 条**，且每条只出现一次。

## 4. 关键重构：它在性质上**不是 warning，而是编辑期诊断**

这是我认为最重要的一点。

| | Lint 警告 | 编译器错误 | **T1 stale** |
|---|---|---|---|
| 出现时机 | 常在后台/每次保存 | 你按下构建那一刻 | **你改完那一刻** |
| 数量 | 与存量成正比 | 与你这次写的错成正比 | **与你这次改的成正比** |
| 是否重复 | 反复出现 | 不重复（改了就消失） | **不重复** |
| 用户态度 | 容易忽略 | 必须处理 | **天然要处理** |

没有人抱怨"编译器又报语法错了"——因为它是**一次性的、可归因的、改动驱动的**。
T1 的 stale 正好落在这个类别里。

**所以疲劳问题不是靠压制解决的，是靠把 stale 从"lint 类别"搬到"编译错误类别"解决的。**

## 5. 「不改变」到什么程度

你的问法是"在不改变的情况下"。精确回答：

| 项 | 要不要变 |
|----|---------|
| `.mq.md` 文档内容 | **不变**（不嵌指纹、不加 `noqa`、不加标记） |
| 写代码 / 读代码的工作流 | **不变**（还是 validate → repair_targets → 编辑 → repair_apply） |
| 项目状态文件 | **不新增**（无台账、无基线、无 `.marqdo/labels.json`） |
| 对 VCS 的依赖 | **无**（沙箱 `exec=false`、WASM 无进程，照样可用） |
| 环境要求 | **无**（纯内存计算） |
| **MLSP 协议** | **加一个可选参数 + 一个响应字段**（这是唯一的改动） |

唯一的协议改动小到可以忽略：

```json
{ "method": "repair_apply",
  "params": { "source": "…", "ranges": [[42,42]], "edits": [...],
              "check_labels": true } }
```

- `check_labels` 缺省 = 不做（**默认零开销、零噪音**）
- 客户端（agent 框架）在修复回路里打开它
- 返回里多一个 `labels` 字段；无 stale 时为空数组

## 6. 配对规则（哪些算"同一条标签"）

比较两份 AST 时：

| 情形 | 判定 |
|------|------|
| 标签文本未变、`()` 指纹变 | ✅ **stale**（核心场景） |
| 标签文本变了 | 不报——作者在更新描述，这就是"确认" |
| `()` 与标签都没变 | 不报 |
| 新插入的标签 | 不报——新断言无历史 |
| 被删掉的标签 | 不报——没有东西可比 |
| 标签移动位置（同文件） | 不报——按标签文本配，不按行号 |

**"按标签文本配对"很关键**：它让"把这段代码挪个位置"不会误报，
而"把这段代码的计算改了"一定报警。

## 7. 模型会不会漏掉？三种兜底

T1 的代价是"不重复"，所以要设计"漏了怎么办"：

| 兜底 | 做法 | 代价 |
|------|------|------|
| **循环预算** | `labels.stale` 非空时，客户端允许下一轮（现有 `max_attempts: 2` 直接可用） | 无 |
| **可选阻塞** | `check_labels: "block"`：apply 成功但返回 `needs_attention: true`，客户端不得结束任务 | 小 |
| **会话末汇总** | 最后一轮给一次总数（只一次，不逐条） | 小 |

**建议默认**：`check_labels: true` + 循环预算。也就是"提示一次，允许一轮修，不强制"。
知识库仓可以用 `"block"`。

---

## 8. 边界（必须说清）

| 问题 | T1 能不能 |
|------|----------|
| 模型刚改完，描述还成立吗 | ✅ 能（核心场景） |
| 昨天有人改了代码，今天打开才发现描述过期 | ❌ 不能（`diff` 里没有，那是 T2 的活） |
| 从别处复制粘贴一段代码带来的旧标签 | ❌ 不能（无历史） |
| 描述写得笼统、无法证伪 | ❌ 不能（L1 也不查） |

**T1 的定位**：保证"**改动者当场被问一次**"。
它不保证"整个仓库始终新鲜"——后者需要 T2/T3，是可选增强，不进默认路径。

---

## 9. 与你担心的「疲劳」对照

| 场景 | 扫描式（每轮全量） | **T1（本机制）** |
|------|------------------|-----------------|
| 模型一轮看到几条 | 全仓库 N 条 | **0–2 条** |
| 5 轮累计 | N × 5 | **≤ 2** |
| 同一标签重复 | 每轮重复 | **一次** |
| 未修复的旧债 | 每轮都提 | 不再提（等它被改到时再说） |
| 模型需要记住"我之前看过" | 需要 | **不需要**（自包含） |
| 需要 VCS / 台账 | 常需要 | **不需要** |

## 10. 待你确认

1. **接受"T1 = 编辑期诊断，不是 lint 警告"这个定位吗？**（这是整个防疲劳论证的支点）
2. `check_labels` 默认值：`false`（零开销）还是 `true`（修复回路默认开）？
3. 漏掉的兜底：用**循环预算**（不强制）还是**可选阻塞**（`"block"`）为默认？
4. 会话末汇总要不要做？（一次性总数，不逐条）

> 若你确认，P1 的第一步就很小：给 `repair_apply` 加 `check_labels`，
> 在 `apply_edits` 之后解析两版、比较标签指纹，把结果挂在响应里。
> 文档零改动、状态零新增、不依赖 git——**第一天就不会有任何存量警告**。
