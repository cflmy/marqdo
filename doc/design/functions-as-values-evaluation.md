## 0. 一句话结论

**你的直觉在数学上是对的，但在语言上要拆成三种强弱不同的主张**：

| 主张 | 是否已成立 | 代价 |
|------|-----------|------|
| 弱：函数**名**可当数据传递 | ✅ **今天就能做**（字符串 + `call_fn`），但零参、不可静态检查 | 无 |
| 中：函数是**一等值**（可存、可传、可返回） | ❌ 需要新值类型 + 动态 callee | 中高：契约、指纹、字节码、序列化全都要动 |
| 强：函数**就是表**（结构性、可遍历、可序列化） | ❌ 需要把代码降格为数据 | **高**：与「代码即文档」的静态可索引性冲突 |

**建议**：把你草图里真正有价值的那部分（**有限域决策表**）作为一等公民支持——它今天就成立、
且极其契合 Marqdo 的表格优先哲学；而「函数即表」的强主张不建议采纳，理由见 §4、§6。

## 1. 先把「函数是变量」拆开

这四个概念经常被混为一谈，必须分开，否则讨论会滑。

### 1.1 外延观（extensional）——函数是「图」

数学上函数就是一组有序对 $f = \{(a,1),(b,2)\}$，即它的**图像**。
按这个观点，函数**确实是一张表**，调用就是**查表**。

**但这里有一个必须先说清的实测事实**（我最初也想当然写错了）：

GFM **两列表绑定成「列映射」，不是「按首列键控的映射」**：

```markdown
`税率` =

| 档位 | 税率 |
|------|------|
| 1    | 0.03 |
| 2    | 0.10 |
```

```json
{"档位":[1,2],"税率":[0.03,0.1]}
```

所以 `[2](`税率`)` **不是**取税率，而是：

```
error: missing map key `2`
```

真正能「键 → 值」查表的形态是 **Map**（来自 JSON 或库函数），实测两条可用配方：

**配方 A（推荐，最简）**

```markdown
**税率 = > json.parse text={"1":0.03,"2":0.10}**
**t = [2](`税率`)**          # → 0.1
```

**配方 B（保留 GFM 表格可读性，但需显式索引）**

```markdown
**ks = [档位](`税率`)**                    # [1, 2]
**vs = [税率](`税率`)**                    # [0.03, 0.1]
**i  = > table.index_of list=`ks` item=2**  # 1
**r  = > table.at xs=`vs` i=`i`**           # 0.1
```

两条都在 1.5.2 上跑通了。**结论**：外延观的「函数=表」在 Marqdo 里不是
`[k](表)` 一句话就能实现，而是「**取到键值对**」这件事本身需要配方。
这恰好是一个可补的库缺口（见 §8.1）。

### 1.2 内涵观（intensional）——函数是「规则」

`f(x) = x² + 1` 无法写成有限表（定义域无穷）。此时函数是**代码**，调用是**执行**。

### 1.3 闭包观——函数是「代码 + 环境」

参数之外还要捕获外部变量。这需要运行时的环境快照。

### 1.4 名字观——函数是「命名空间里的一条」

今天 Marqdo 就是这一种：函数存在于 `Module.functions`，按名字解析。

**你的草图 `|参数|函数体|` 属于哪一种？** 它是**混合体**：行是参数声明（§1.4 的味道），
单元格放函数体（§1.2 的味道）。而「和表格取元相似」的直觉来自 §1.1。
**三种东西被一句话连起来了**——这正是评估要解开的结。

## 2. 现状实测（全部在 1.5.2 上跑过）

### 2.1 值模型里没有函数

`src/value.rs:15` 的 `Value` 枚举：`None / Bool / Int / Num / Text / List / Map / Formula / Code / Secret`。
**没有 `Func`。** 函数是 AST 节点（`src/ast.rs:58 Function`），挂在 `Module.functions`（`src/ast.rs:27`）。

`src/contract.rs:104` 的 `type_of` 同样是十种，穷举无函数。

### 2.2 调用的 callee 是静态名字，不是表达式

`src/ast.rs:130 CallExpr { callee: String, path, receiver, args }` ——
`callee` 是 **`String`**，不是 `Expr`。所以**语法上无法写出「对计算出来的值发起调用」**。

运行期 `src/interp.rs:1119 eval_call` 最终走到 `lookup_function`（`src/interp.rs:1774`），
按名字在 AST 树里查找。

### 2.3 对象已经是「表」

`src/interp.rs:1509 instance_type_name` 要求 method receiver 是**带 `_type` 键的 Map**：

```
error: method receiver needs a map with `_type`
```

也就是说 **Marqdo 里「用户定义的结构」本来就是普通 map + 一个标签**。
对象与表之间没有鸿沟——**这与你的直觉一致，而且已经是既成事实**。

但函数不是。对象是值，函数不是。这个不对称值得注意。

### 2.4 已存在按名字间接调用：`call_fn`

`src/interp.rs:1295`：

```rust
"call_fn" => {
    // name 必须是 text
    let target = lookup_function(module, fun, name)...;
    if !target.params.is_empty() {
        return Err("call_fn: `{name}` must have no parameters");
    }
    self.run_function(module, target, Env::new(), &[], false)
}
```

这是**今天最接近「函数可传递」的机制**，但有三道硬限制：零参、限当前模块、只在运行期校验。

### 2.5 六组实验

| # | 写法 | 结果 | 结论 |
|---|------|------|------|
| 1 | `**f = > greet**` | `missing argument for parameter who` | `> 名字` 是**调用**语法，**无法引用函数本身** |
| 2 | `> call_fn name="hello"`（无参函数） | `world` | 按名字调用可行 |
| 3 | `> call_fn name="add"`（有参） | `call_fn: `add` must have no parameters` | 不能传参 |
| 4 | 表里存函数名 + `[h](reg)` 取名 + `call_fn` | `dispatch=world` | **动态派发今天就能做**（名字即数据） |
| 5 | `> call_fn name="txt.str_trim"` | `unknown function` | **不能跨模块** |
| 6 | `> call_fn name="no_such_fn"` | `unknown function` | 拼错只能在**运行期**发现 |

**实验 4 是关键**：它已经是「函数作为表成员」的可用原型，只是把函数表示成**名字字符串**而不是函数值。

## 3. 你的类比中成立的部分

必须明确肯定，否则会低估这个想法。

### 3.1 「有限域函数 = 表」是完全成立的范式

这类函数在工程里非常常见，而且用它表达比写代码更清楚：

| 场景 | 适合表格 | 为什么 |
|------|---------|--------|
| 税率 / 费率档位 | ✅ | 有限、离散、常改动 |
| 状态机转移表 | ✅ | 二维查表一目了然 |
| 错误码 → 处理动作 | ✅ | 业务方直接维护 |
| 路由分发 | ✅ | 键即路径 |
| 配置映射 | ✅ | 本来就是数据 |

而且 Marqdo 的 `[键](集合)` 取元**在语义上就是函数应用** ——
前提是这个集合是 **Map**（键→值）：

```markdown
**rate = [2](`税率`)**       # 读作：税率(2)
```

只要 `税率` 是 Map，这行**无需任何语言改动**就是一个查表函数。你已经拥有它了。

唯一的坑是**数据形态要对**：GFM 两列表绑定的是**列映射**（§1.1 实测），
`[2](两列表)` 会报 `missing map key`。所以「表 = 函数」成立，
但**哪种表**有讲究——这正是 §8.1 要补 `table.by_column` / `table.lookup` 的原因。

### 3.2 表格对「参数边界」天然友好

上一轮讨论 `[函数名](参数)` 时，痛点是参数边界（空格切词）。表格完全绕开这个问题：
键是**显式**的，不需要切词。

### 3.3 对象已证明「结构即表」不会损害语言

§2.3 说明对象本来就是 map。既然对象能这样，把**数据的**函数化交给表格是自洽的。

## 4. 类比的断裂点

三个，每一个都是硬约束。

### 4.1 断裂点一：表格是有限的，函数通常是无限的

外延观只对**有限定义域**成立。`f(x)=x²+1` 写成表需要无限行。
所以「函数即表」只能覆盖**查表能解决的那部分**，不能作为函数的通用表示。

一旦你承认这一点，「函数即表」就从「函数的定义方式」降级为「一种特殊函数（图表函数）」。
这仍然有用，**但不是语言的核心函数机制**。

### 4.2 断裂点二：函数体是**代码**，不是数据

你的草图把「函数体」放进单元格。但函数体在 Marqdo 里是 `Vec<Stmt>`（AST），不是 `Value`。
要让函数体成为单元格内容，必须先让「代码」成为值——即 `Value::Code` 那种东西。

而 `Value::Code` 目前**只表示外联语言源码**（```lang 围栏），是交给外部执行器跑的，
不是 Marqdo 自己的代码。让 Marqdo 代码变成值 = 引入 `eval`，这会带来：

- 静态检查失效（代码在运行期才成形，`marqdo check` 看不见）
- EKC 指纹失效（§6.2）
- 契约失效（§6.1）

### 4.3 断裂点三：调用不是取元——`[k](x)` 会被语义重载

这是最要命的一条，**与上一轮 `[函数名](参数)` 的冲突同源**。

若「函数是表」且「调用 = `[参数](函数表)`」，那么：

```markdown
[a](m)        # m 是普通 Map → 取成员 a
[参数](f)      # f 是「函数表」→ 执行？还是取成员「参数」？
```

**形状完全一致，含义取决于值的类型**。这正是上一轮我们判定「不可靠消歧」的同一类问题，
只不过从「语法层歧义」升级成了「类型层重载」。

Marqdo 的 `[k](coll)` 目前是**唯一且清晰**的取元语义。让它兼职「调用」，
会让最常用的读表操作变得需要思考「这个表是不是函数」。

## 5. 五条设计路径

### 路径 A — `Value::Func` 闭包（一等函数）

```rust
Value::Func(Rc<FuncVal>)   // params + body + captured Env
```

调用点需支持「对表达式求值后再调用」，即 `CallExpr.callee` 从 `String` 变成 `Callee::Name(String) | Callee::Expr(Expr)`。

**代价**：

| 面 | 影响 |
|----|------|
| 契约（T2.1/T2.2） | `call_arg_diag(c, &target.name, …)` 依赖静态 `target: &Function`；动态调用**拿不到**，契约检查只能退化为运行期 |
| 字节码 | `Op::Call(fid, argc)` 用**编译期函数 id**（`src/bytecode/compile.rs:709`），动态 callee 需要新指令或回退树遍历 |
| EKC 指纹 | `collect_calls` 读 `c.callee`（`src/knowledge/fingerprint.rs:76`），动态调用只剩字面 `call_fn`，**复用/查重能力下降** |
| 序列化 | `value_to_json`（`src/host/json.rs:98`）对 `Value` 穷举，函数值必须定义 JSON 语义（丢弃？报错？） |
| 沙箱 | 函数值无法跨沙箱边界，`sandbox.run` 的接口要加限制 |
| 闭包捕获 | 需要环境快照与生命周期管理；`Env` 目前是每次调用新建（`Env::new()`） |

**适用于**：确有高阶需求（回调、map/filter、事件处理）。属于**新语言特性**，应走 ADR。

### 路径 B — 函数即表（你的草图，强主张）

**代价**：A 的全部，**外加** §4.3 的语义重载，以及：

- 表可以 `table.put` 被修改 → 函数可变？还是只读？
- 表可以遍历 → 遍历函数会看到什么？参数名？函数体 AST？
- 表可以 `json.stringify` → 函数体以什么形式序列化？
- 宏展开式的能力（代码即数据）会引入**自修改程序**，与「可静态审计」直接冲突

**结论**：**不建议**。它把 Marqdo 从「可静态索引的文档程序」推向「运行期构造的代码」，
是在削弱自己最强的差异点（§6）。

### 路径 C — 对象可调用（复用 `_type` + 约定方法）

让 `# 类名` 实例在 `_type` 之外带一个约定的 `## 应用` 方法，`f(x)` 时若 `f` 是 map 且 `_type` 有该方
法则走方法调用。

**优点**：不新增 `Value` 变体；复用既有 method 机制。
**缺点**：仍需要「`f(x)` 里 f 是表达式」这一语法能力（同 A 的调用点改造）；
且引入「有的 map 可调用」的隐式规则，可读性下降。

### 路径 D — 名字即函数（扩展现有 `call_fn`）

不引入函数值，而是把**名字**这条路径做完整：

```markdown
> call_fn name="add" args=[1, 2]           # 支持传参
> call_fn name="txt.str_trim" args=[…]     # 跨模块路径
> invoke table=`注册表` key="h" args=[…]    # 从表里按名派发
```

**优点**：
- 零值模型改动 → 契约、字节码、指纹、序列化**全部不动**
- 保持「函数永远有名字」→ EKC 能索引，代码可审计
- 与实验 4 的现有用法完全兼容（只是补齐能力）

**缺点**：不是真正的一等函数（不能返回闭包）；名字拼错仍要运行期发现
（但**可以**加静态检查：`call_fn name="字面量"` 时校验目标存在——见 §8.2）。

### 路径 E — 决策表作为一等公民（**推荐方向**）

不叫它「函数即表」，而明确它是什么：**有限域查表函数**。

```markdown
**税率 = > json.parse text={"1":0.03,"2":0.10}**    # Map：键 → 值
**t = [2](`税率`)**                                  # 今天就能跑 → 0.1
```

**优点**：**零语言改动**，只需文档与库函数支持（例如 `table.lookup` 带默认值，
把 §1.1 配方 B 的「列取 + 索引」四步压成一步）。
**定位诚实**：它是数据，不是代码；能被 EKC 索引、能序列化、能进沙箱、能被非程序员维护。

## 6. 对 Marqdo 特有机制的冲击面

这一节是决策的关键：Marqdo 不是通用语言，它的价值在**可静态索引的工程知识**。

### 6.1 契约系统（T2.1 / T2.2）

现有实现把契约挂在 `Function` 上（`src/ast.rs:71`），并在调用点用**静态 target**校验：

```rust
if let Some(c) = &target.contract {
    if let Some(d) = contract::call_arg_diag(c, &target.name, &bound, …) { … }
}
```

动态 callee 拿不到静态 `target`，**契约检查必然退化到运行期**——而契约是 Marqdo
「渐进式契约」卖点的核心。

### 6.2 EKC 指纹与复用

`collect_calls` 把调用目标名字写进指纹（`src/knowledge/fingerprint.rs:76`）。
指纹用于**查重、复用预检、相似任务召回**。动态调用使指纹丢失真实目标，
`marqdo duplicate` / `preflight` 的准确率会下降——这直接影响智能体复用飞轮。

### 6.3 「函数必须有名字」是特性，不是限制

EKC 按符号名索引（`marqdo knowledge` 输出 `59 modules, 346 symbols`）。
匿名函数/表构造的函数**无法被索引**，也就无法被复用、被审计、被智能体发现。

> 对 Marqdo 而言，**函数有名字**不是妥协，而是「代码即文档」的必然：
> 文档里的每一段代码都得有一个可被引用的标题。

### 6.4 序列化与沙箱

`value_to_json` 穷举所有 `Value`。函数值需要 JSON 语义；
沙箱（CoW + 禁 exec/net/plugin）跨边界传值时，函数**无法表示**。
一旦函数成为值，`sandbox.run` 的入参约束必须收紧。

### 6.5 确定性与可审计

表格是**静态可读**的：非程序员能改税率表。代码构造的函数则要求读者在脑中执行程序。
Marqdo 面向的是「文档作者也能维护」的场景，这一点权重很高。

| 保持静态可索引 | 部分（匿名不可） | ❌ | ✅ | ✅ | ✅ |
| 契约检查 | **退化** | 退化 | 保持 | 保持 | 保持 |
| EKC 指纹 | 退化 | 退化 | 保持 | 保持 | 保持 |
| 序列化/沙箱 | 需特殊处理 | 需特殊处理 | 保持 | 保持 | 保持 |
| 解决参数边界 | ✅ | ✅ | ✅ | ✅ | ✅ |

## 8. 建议（分阶段）

### 8.1 立即可做：决策表（路径 E）

零语言改动。补三件事即可让它好用：

1. **补库缺口**：新增 `table.lookup map=`key=`default=`（键→值，缺键返回 default）与
   `table.by_column rows=`key_col=`value_col=`key=`（把 §1.1 配方 B 的四步压成一步）。
   **这是当前最实的缺口**——GFM 两列表无法直接键查表，用户会反复手写索引逻辑。
2. **文档**：在教程里明确「有限域映射怎么表达」，并给出三种形态的取舍：
   - 键→值查表 → `json.parse` 的 Map + `[键](map)`
   - 需要保留表格可读性 → 两列表 + `table.by_column`
   - 缺键行为 → 用 `table.get` / `default=`，避免缺陷 D5 的 `missing map key` 硬崩
3. **命名**：明确它叫「决策表 / 查表」而不是「函数」——避免与 §1.2 的内涵观混淆。

**价值**：把用户已有的直觉固化成推荐用法，不付任何架构代价。

### 8.2 短期可做：扩展 `call_fn`（路径 D）

补齐三件事，都不触及值模型：

| 补充 | 说明 |
|------|------|
| `args=` | 允许传参，按目标签名绑定 |
| 跨模块路径 | `name="lib.fn"` 走 import 解析 |
| 字面量静态校验 | `call_fn name="字面量"` 在 `check` 期就校验目标存在（消灭实验 6 的类错误） |

**收益**：动态派发能力完整，且完全保留契约/指纹/序列化。

### 8.3 中期评估：一等函数（路径 A）

只有当出现**确实无法用名字表达**的需求时才做（例如回调、策略模式、事件处理器）。
届时必须写 ADR，并明确回答：

- 匿名函数如何进入 EKC 索引？（可能需要要求「赋给变量的函数字面量必须有名字」）
- 契约在动态调用下如何降级？
- 字节码是否引入 `Op::CallValue`？
- 函数值的 JSON 语义是什么？

### 8.4 不建议：路径 B（函数即表，强主张）

理由汇总：§4.3 语义重载 + §6 全面削弱静态可索引性 + §5 自修改程序风险。

## 9. 如果你想保留「函数即表」的形态，有一个折中

把「表」用于**参数与分发**，而不用于函数体：

```markdown
`税率表` =

| 档位 | 税率 |
|------|------|
| 1    | 0.03 |
| 2    | 0.10 |

## 税率
    + `档位`

**ks = [档位](`税率表`)**
**vs = [税率](`税率表`)**
**i = > table.index_of list=`ks` item=`档位`**
**r = > table.at xs=`vs` i=`i`**
*r*
```

（若 §8.1 的 `table.by_column` 落地，函数体可缩成一行：
`**r = > table.by_column rows=`税率表` key_col="档位" value_col="税率" key=`档位`**`。）

这里：

- **数据**在表里（可被非程序员维护、可序列化、可进沙箱、可被 EKC 索引）
- **逻辑**在命名函数里（可契约、可指纹、可审计）
- 调用仍是一等清晰的 `> 税率 档位=2`

这其实是**最好的分工**：表格承担「知识」，函数承担「行为」。
它同时满足你的类比直觉（表驱动）和 Marqdo 的静态可索引性。
