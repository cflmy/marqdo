可以。基于你现在的 `ext/ai/agent` 实现，我建议不要把它继续做成一个“带缓存的 LLM Agent”，而是正式把它定义成：

> **一个能够把执行经验逐渐编译成 `.mq.md` 可执行知识/技能的自学习智能体运行时。**

你现在的框架其实已经有不少基础：`step` 负责单步 LLM/tool execution，`plan` 负责多步执行，并且已经有 `exact → alias → canonical → near` 的复用路径、`agent-kb`、`explore_n`、`improve_every`、`llm_free` 和执行事件记录。 

下面我给你一套可以直接作为 **Marqdo Agent Framework v2 设计文档** 的方案。

# Marqdo Agent Framework v2

## 1. 核心目标

整个 Agent 不应该只是：

```text
Task
 ↓
LLM
 ↓
Tool
 ↓
Answer
```

而应该变成：

```text
                 ┌─────────────────────┐
                 │      User Task      │
                 └──────────┬──────────┘
                            ↓
                    ┌───────────────┐
                    │ Skill Resolver│
                    └───────┬───────┘
                            │
            ┌───────────────┼────────────────┐
            ↓               ↓                ↓
        Exact Skill      Similar Skill     Unknown
            │               │                │
            ↓               ↓                ↓
       MQ Execution     Adaptation       Exploration
            │               │                │
            └───────────────┼────────────────┘
                            ↓
                       Verification
                            ↓
                         Result
                            ↓
                      Episode Trace
                            ↓
                    Experience Store
                            ↓
                 Pattern / Skill Mining
                            ↓
                    Candidate Skill
                            ↓
                       Validation
                            ↓
                     Skill Compile
                            ↓
                   Executable .mq.md
                            │
                            └───────────────→ 下一次调用
```

因此 Agent 有两个完全不同的阶段：

### Online

解决当前任务：

```text
Resolve → Execute → Verify → Return
```

### Offline / Background

从历史经验中学习：

```text
Collect → Cluster → Generalize → Validate → Compile
```

这是整个设计最重要的结构。

---

# 2. Agent 的四种“记忆”

我建议不要把所有东西都叫 Memory。

实际上应该有四层。

## 2.1 Episode Memory

记录：

> “这一次具体发生了什么？”

例如：

```text
episode/
    20260924-001.mq.md
    20260924-002.mq.md
    20260924-003.mq.md
```

它是**情景记忆**。

记录：

```yaml
task
context
decision
actions
tool_calls
observations
errors
result
verification
cost
```

它不需要漂亮，也不需要高度抽象。

---

# 3. Experience Memory

Episode 多了以后，系统开始发现：

```text
Episode 1
Episode 2
Episode 3
Episode 4
     ↓
这些任务其实属于同一个模式
```

于是形成：

```text
experience/<slug>.mq.md
```

例如：

```text
experience/
    extract-json-from-response.mq.md
    search-local-corpus.mq.md
    repair-invalid-json.mq.md
```

Experience 是：

> 多次执行中发现的稳定模式。

---

# 4. Skill Memory

Experience 进一步经过验证以后，变成：

```text
skills/<slug>.mq.md
```

这个文件已经不是“记录”。

它是：

> **可以直接执行的程序。**

例如：

```markdown
---
type: skill
status: compiled
llm_free: true

success_rate: 0.96
confidence: 0.98
evidence: 31

input:
  - query

output:
  - result

fallback: llm
---

## main

1. `query`
   > corpus_search query=`query`

2. `result`
   *result*
```

这才是 Marqdo 最特别的地方：

> **Agent 的学习结果最终不是 embedding，而是 `.mq.md`。**

---

# 5. Policy Memory

这是进一步优化。

某些技能虽然不能完全 deterministic，但可以让一个小模型决定：

```text
if task.kind == "json":
    use json-repair
elif task.kind == "search":
    use corpus-search
else:
    use llm
```

于是形成：

```text
policy/
    router.mq.md
    json-router.mq.md
```

所以最终可以形成：

```text
Episode
   ↓
Experience
   ↓
Skill
   ↓
Policy
```

# 6. Agent 的核心状态机

我建议 Agent 明确定义以下状态：

```text
NEW
 │
 ↓
RESOLVE
 │
 ├── EXACT HIT ────────→ EXECUTE
 │
 ├── NEAR HIT ─────────→ ADAPT
 │
 └── MISS ─────────────→ EXPLORE
                            │
                            ↓
                         EXECUTE
                            │
                            ↓
                         VERIFY
                            │
                  ┌─────────┴─────────┐
                  ↓                   ↓
                FAIL                 PASS
                  │                   │
                  ↓                   ↓
                REPAIR             RECORD
                  │                   │
                  └───────→          ↓
                              EPISODE
                                  │
                         enough evidence?
                           │          │
                          no         yes
                           │          │
                           ↓          ↓
                         DONE      LEARN
                                      │
                                      ↓
                                  CANDIDATE
                                      │
                                      ↓
                                   VALIDATE
                                   /      \
                                FAIL      PASS
                                 │          │
                                 ↓          ↓
                              REJECT     COMPILE
                                            │
                                            ↓
                                         SKILL
```

这个状态机应该成为 `plan()` 的真正语义。

现在的 `plan()` 已经在做其中的一部分，例如 reuse、explore、await、revise 和 promote。

# 9. `agent.step`

你现在的 `step` 应该保留。

它是 Agent 最基础的 primitive。

当前 `step` 已经承担：

```text
context assembly
→ LLM
→ READ
→ CALL
→ history
→ writeback
```

这正适合作为底层执行单元。

建议正式定义：

```text
## step
    + `task`
    + `context`=None
    + `skill`=None
    + `tools`=None
    + `model`=auto
    + `budget`=None
    + `mode`=reason
```

其中：

```text
mode =
    deterministic
    rule
    small_model
    llm
    explore
```

# 10. `agent.resolve`

这是新版 Agent 最重要的函数之一。

```text
## resolve
    + `task`
    + `kb_dir`
    + `near_match`=True
    + `threshold`=0.78
```

返回：

```json
{
  "mode": "near",
  "skill": "json-repair",
  "resource": ".marqdo/agent-kb/skills/json-repair.mq.md",
  "score": 0.91,
  "confidence": 0.97
}
```

Resolver 应该按：

```text
1. exact
2. alias
3. canonical
4. near
5. semantic
6. policy
7. unknown
```

寻找技能。

你现在已经实现了：

```text
exact
alias
canonical
near
soft
```

所以这一部分可以直接演进，而不是重写。

# 11. `agent.execute`

Resolver 决定怎么执行之后：

```text
## execute
    + `task`
    + `resolution`
```

例如：

```text
resolution.mode == compiled
```

直接：

```text
await_workbook(skill)
```

而不是：

```text
LLM → 再想一遍
```

如果：

```text
resolution.mode == near
```

则：

```text
skill
 ↓
parameter adaptation
 ↓
execute
 ↓
verify
```

如果：

```text
resolution.mode == unknown
```

则：

```text
LLM exploration
```

# 12. Cognitive Cost Ladder

我非常建议把它正式加入框架。

```text
L0  deterministic
        ↓
L1  Marqdo rule / branch
        ↓
L2  small decision model
        ↓
L3  small LLM
        ↓
L4  full LLM
        ↓
L5  exploration / multi-step reasoning
```

每一个任务都应该有：

```text
cost_level
```

例如：

```yaml
cost_level: 0
llm_calls: 0
```

或者：

```yaml
cost_level: 4
llm_calls: 7
```

学习的本质就是：

```text
L5
 ↓
L4
 ↓
L3
 ↓
L2
 ↓
L1
 ↓
L0
```

这会成为 Marqdo Agent 非常漂亮的研究指标。

# 13. `agent.verify`

不能：

```text
成功一次
→ 自动成为 skill
```

否则很容易错误泛化。

所以必须有：

```text
## verify
    + `task`
    + `result`
    + `skill`=None
    + `evidence`=None
```

验证包括：

### 13.1 Execution verification

```text
有没有报错？
```

### 13.2 Structural verification

```text
输出格式是否正确？
```

### 13.3 Semantic verification

```text
结果是否真正解决 task？
```

### 13.4 Regression verification

```text
过去的任务还能不能通过？
```

```text
1 execution
    ↓
episode

2 execution
    ↓
episode

candidate skill
```

```text
candidate
    ↓
historical replay
    ↓
held-out test
    ↓
verification
```

成功以后才：

```text
compiled
```

# 16. `agent.cluster_episodes`

Episode 太多以后不能每次全量交给 LLM。

因此：

```text
## cluster_episodes
    + `episodes`
    + `threshold`=0.82
```

目标：

```text

episode 3 ─┤→ cluster A
episode 4 ─┘
```

可以先使用：

```text

+
```

不要一开始就让大模型处理所有历史。

# 18. `agent.generalize`

这个函数非常重要。

```text
## generalize
    + `pattern`
    + `episodes`
```

例如：

三个任务：

```text
修复 JSON
修复 YAML
修复 TOML
```

可能共同形成：

```text
parse structured data
→ validate
→ locate syntax error
→ repair
→ validate again
```

但是：

```text
JSON/YAML/TOML
```

应该成为：

```text
format
```

而不是写死。

最终：

```yaml
input:
  format
  text

procedure:
  parse(format)
  validate()
  repair()
  validate()
```

这才叫 **Generalization**。

# 21. 为什么一定需要 Held-out Test？

否则：

```text
Episode A
Episode B
Episode C

→ 从 A/B/C 总结 Skill

→ 再用 A/B/C 测试
```

这会产生：

> 训练数据泄漏。

所以应该：

```text
A B C D E F G
│ │ │ │ │ │ │
├─┴─┴── training
│
└────── validation
```

例如：

```text
5 个 episode
→ 3 个学习
→ 2 个测试
```

当数据不足时：

```text
candidate
```

而不是：

```text
compiled
```

# 22. `agent.compile`

```text

    + `validation`
```


# 29. `agent.maybe_learn`

`run()` 不应该每次都学习。

因此：

```text
## maybe_learn
    + `task`
    + `episode`
```

判断：

```text
是否存在类似任务？
是否达到 evidence threshold？
是否出现稳定 tool sequence？
是否成功率足够？
是否值得编译？
```

例如：

```text
episode_count >= 3
AND
similarity >= 0.85
AND
success_rate >= 0.90
```

才触发。

# 30. `improve_every` 的重新定义

你现在已经有：

```text
improve_every=3
```

当前语义更接近：

> 命中一定次数之后进行改进。



我建议升级成：

```yaml
learning:
  trigger_every: 3
  validation_min: 3
  confidence_min: 0.90
  success_rate_min: 0.92
```

然后：

```text
trigger_every
```

只代表：

> 什么时候重新检查技能。

而不是：

> 什么时候自动修改技能。

# 31. `explore_n` 重新定义

你当前：

```text
explore_n=3
```

会在任务文件不足时强制探索不同 variant。

这个设计其实非常好，但应该明确：

```text
explore_n = exploration budget
```

而不是简单：

```text
没有 skill → 多跑三次
```

建议：

```text
exploration strategy:
    variant A
    variant B
    variant C
```

比如：

```text
A: tool-first
B: code-first
C: LLM-first
```

然后比较：

```text
success
latency
tokens
tool calls
robustness
```

最终选择。

# 33. `agent.select_strategy`

```text
## select_strategy
    + `candidates`
```

不是简单按照：

```text
success
```

而是：

```text
utility =
    correctness
    - λ * token_cost
    - μ * latency
    - ν * tool_cost
```

例如：

```text
A:

tokens = 8000

B:
success = 0.94
tokens = 1000

C:
success = 0.99
tokens = 3000
```

系统可以保存：

```text
strategy profile
```

而不是每次重新思考。

# 34. 这就引出你之前说的 Jev

# 47. `plan()` 最终应该变成什么

这是最重要的一点。

你现在的 `plan()` 实际上已经非常庞大，因为它同时承担：

```text
reuse
explore
decompose
execute
await
revise
promote
stream
trace
```

当前实现中 `plan` 已经包含这些职责，例如 reuse 命中后直接 await workbook、探索新 variant、执行后 revise，以及成功后的 KB promotion。

**v2 不应该继续往 `plan()` 里面塞逻辑。**

应该把：

```text
plan()
```

变成 orchestrator：

```text
## plan

resolve
↓
route
↓
execute
↓
verify
↓
record
↓
learn
↓
finish
```

真正的逻辑全部下沉到函数。

即：

```text
plan
 ├── resolve
 ├── route
 ├── execute
 ├── verify
 ├── record_episode
 └── maybe_learn
```

这样 `plan` 才会重新变得可读。

# 50. Marqdo Agent 的最终定义

我会把整个系统概括成：

```text
                    MARQDO AGENT
                         │
             ┌───────────┴───────────┐
             │                       │
        ONLINE RUNTIME          LEARNING RUNTIME
             │                       │
       ┌─────┴─────┐           ┌─────┴─────┐
       │           │           │           │
    Resolve     Execute     Episodes    Patterns
       │           │           │           │
       ↓           ↓           ↓           ↓
     Route       Verify      Cluster    Generalize
       │           │           │           │
       └─────┬─────┘           └─────┬─────┘
             │                       │
             ↓                       ↓
           Result                Candidate
                                     │
                                     ↓
                                  Validate
                                     │
                                     ↓
                                  Compile
                                     │
                                     ↓
                              Executable MQ
                                     │
                                     └────→ ONLINE
```

所以它不是：

> **Agent + Memory**

而是：

> **Agent = Runtime + Experience + Learning + Compiler**

进一步说：

> **Marqdo Agent 的“记忆”不是存储过去发生过什么，而是把过去发生过的事情编译成未来可以执行的知识。**

这句话其实非常适合成为你整个 Agent Framework 的设计核心。
