> **Marqdo 真正有机会形成差异化的地方，不是“AI 可以用 Markdown 写代码”，甚至也不只是“Markdown 是可执行知识库”，而是：让一个大型工程本身成为 AI 可查询、可验证、可复用、可演化的“可执行知识系统”，从而在代码生成前就知道“工程里已经有什么、应该复用什么、为什么不能重新造”。**

这比“RAG + Coding Agent”要更深一层。

目前仓库 README 已经明确把目标定义为“代码即文档、文档即代码、文档即知识库”，并且已经有 `catalog/sync`、自动生成 `catalog.yaml` / `index.md` / `modules/*.md` 的基础设施。([GitHub][1])
同时，新的 Agent 设计也已经明确：源码、调用位置、Skill、工作簿和写回结果都应该进入 Agent 上下文，而且成功/失败结果应该沉淀，而不是只存在于 chat transcript。([GitHub][2])

**现在真正缺的，是把这两个方向合成一个“工程知识编译器”。**

# 一、我先给出我认为 Marqdo 应该最终形成的核心模型

我建议不要再把 Marqdo 简单理解成：

```text
Markdown
   ↓
Programming Language
   ↓
AI Agent
```

而应该是：

```text
                    Git Repository
                         │
             ┌───────────┴───────────┐
             │                       │
          Source                  Documents
             │                       │
             └───────────┬───────────┘
                         ↓
                  Marqdo Compiler
                         │
          ┌──────────────┼──────────────┐
          ↓              ↓              ↓
      Executable      Knowledge       Catalog
       Program         Graph          / Index
          │              │              │
          └──────────────┼──────────────┘
                         ↓
                  Engineering KB
                         │
                         ↓
                    Coding Agent
                         │
              ┌──────────┼──────────┐
              ↓          ↓          ↓
           Search      Reuse      Generate
              │          │          │
              └──────────┼──────────┘
                         ↓
                  Verified Change
                         │
                         ↓
                  Knowledge Update
                         │
                         └──────→ Git
```

也就是说：

> **Marqdo 不应该只是帮助 AI “写代码”，而应该帮助 AI 在写代码之前理解工程。**

这才是大型工程场景真正困难的事情。

# 二、为什么“大规模工程 AI”真正的问题不是生成能力

现在的 Coding Agent 最大的问题往往不是：

> “AI 不会写这个函数。”

而是：

> **“AI 不知道这个函数已经存在。”**

或者更隐蔽：

> “AI 知道有类似函数，但不知道哪个才是应该复用的。”

再进一步：

> “AI 找到了一个类似函数，但不知道这个函数为什么这样设计。”

再进一步：

> “AI 找到了正确函数，但是不知道它有哪些隐含约束。”

例如一个大型工程里可能已经存在：

```text
parseConfig()
loadConfig()
resolveConfig()
normalizeConfig()
mergeConfig()
validateConfig()
readConfigFile()
```

用户让 AI：

> “实现一个配置加载功能。”

普通 Coding Agent 很可能：

```text
搜索几个文件
↓
发现没完全一样
↓
写一个新的 load_configuration()
↓
加 300 行代码
↓
测试通过
```

从局部看：

> 成功。

从工程看：

> **失败。**

因为真正正确的行为可能是：

```text
resolveConfig()
    +
validateConfig()
    +
已有错误处理
```

AI 的核心问题其实是：

```text
工程知识缺失
        ↓
无法识别已有能力
        ↓
重复实现
        ↓
代码碎片化
        ↓
维护成本上升
```

---

# 三、所以我建议 Marqdo 提出一个非常明确的概念

## Engineering First Information

我会把它定义成：

> **Engineering First Information（工程第一信息）**

也就是：

> AI 在修改/生成代码之前，首先获得关于当前工程中已有能力、约束、依赖、约定、历史决策和可复用实现的最小充分信息。

这个概念非常适合成为 Marqdo 的核心论文/产品概念。

因为普通 RAG 是：

```text
query
 ↓
retrieve documents
 ↓
LLM
```

而 Marqdo 应该是：

```text
engineering task
 ↓
understand intent
 ↓
retrieve engineering first information
 ↓
reuse analysis
 ↓
existing capability candidates
 ↓
architecture constraints
 ↓
only then generate
```

区别非常大。

# 七、它和普通 OKF 有什么区别？

这里要特别注意。

OKF 本身是一个**开放的知识包装格式**：Markdown + YAML frontmatter，强调人和 Agent 都能读、能版本控制、能交换。官方规范刻意保持简单，不要求 schema registry 或特定工具。([GitHub][3])

所以：

> **不要把 Marqdo 做成“另一个 OKF”。**

应该：

```text
OKF
 ↓
Knowledge Packaging Layer

Marqdo
 ↓
Engineering Knowledge Execution Layer
```

也就是：

```text
OKF
    ↓
Marqdo Engineering Profile
    ↓
Executable Engineering Knowledge
```

这是我认为最优雅的关系。

# 九、这是解决“AI 重复造轮子”的关键

```text

Candidate #3

score: 0.71

```

于是模型不再：

> “我要写一个 config loader。”

而是：

> “工程里已经有 `resolve_config`，我应该调用它。”

# 十四、三个状态分别代表什么

### REUSE

已有能力满足需求。

```text
直接调用
```

---

### ADAPT

存在相近能力。

```text
包装
组合
参数化
扩展
```

例如：

```text
A
 +
B
 →
新的 capability
```

而不是复制 A。

---

### CREATE

经过检索和分析确认：

> 工程中不存在合适能力。

才允许生成。

这个顺序应该成为 Marqdo Agent 的**硬规则**：

```text
REUSE
  ↓
ADAPT
  ↓
CREATE
```

而不是：

```text
CREATE
  ↓
maybe reuse
```

# 二十二、再增加一种极其重要的知识：Negative Knowledge

我认为这是 Marqdo 可以做得非常漂亮的地方。

## Correct approach

## Introduced by

> “我要缓存权限判断。”

这比一般 RAG 强得多。

## 我建议你下一阶段不要继续无边界地给 `agent-kb` 加功能

而是直接做一个 **Marqdo Engineering Knowledge v1**。

优先级我会这样排：

| 阶段     | 要做的东西                           | 目标                                |
| ------ | ------------------------------- | --------------------------------- |
| **P0** | Symbol Catalog                  | AI 知道工程里有什么                       |
| **P0** | Capability Catalog              | AI 知道工程能做什么                       |
| **P0** | `reuse/preflight`               | 生成前强制检查已有能力                       |
| **P0** | Context Pack                    | 给模型第一信息，而不是整个 repo                |
| **P1** | Decision / Constraint / Failure | 让 AI 知道为什么、禁止什么、过去错过什么            |
| **P1** | Dependency / Call / Test Graph  | 建立工程知识图                           |
| **P1** | Duplicate Detection             | 检测 AI 新造的重复能力                     |
| **P1** | Knowledge Lifecycle             | stale / deprecated / superseded   |
| **P2** | Policy Compilation              | 将复用判断编译成 `.mq.md`                 |
| **P2** | Knowledge Compilation           | 从执行经验自动生成知识                       |
| **P2** | Reuse CI Gate                   | PR 阶段阻止重复造轮子                      |
| **P3** | Knowledge-aware Agent           | Agent 原生依赖 Engineering Knowledge  |
| **P3** | Benchmark                       | 用重复率、检索召回、token amortization 衡量优势 |

其中我认为真正的 **P0 只有三个核心组件**：

```text
Capability Catalog
        +
Reuse Preflight
        +
Engineering Context Pack
```

这三个做出来，Marqdo 就第一次真正开始具备你说的：

> **“让 AI 在大型工程中获得第一信息，并减少重复造轮子”的能力。**

而且这条路线并不需要抛弃现在的 OKF、`catalog`、`agent-kb`、`writeback` 和 `plan`；恰恰相反，**它们可以全部成为这个架构的基础设施。**

官方仓库目前已经明确把自动 Catalog、可执行 `.mq.md`、OKF 风格清单和 Agent 工作簿放在同一条产品主线上。([GitHub][1])
我认为下一步最重要的不是再增加一个功能，而是把这些东西**正式统一成一个“Engineering Knowledge Compiler”架构**。

如果这个方向成立，Marqdo 最终真正独特的东西可能不是 `.mq.md` 这个语法本身，而是：

> **一个大型代码仓库在 Marqdo 中可以同时作为程序、文档、知识图谱、Agent 上下文和可复用能力目录存在，而且这些视图全部由同一份可执行源代码派生。**
