# main

诚实的说，作者其实一直都很纠结说marqdo是否具有存在的必要，不过在逐渐的开发和了解中，marqdo
是有价值的，我此时此刻确信这一点。

在过去的很长时间中，我一直在思考，marqdo代码即文档，文档即知识库，知识库可执行有什么作用呢？

## code as document,document as skill,skill is tools

现在我给出的答案是，code as document,document as skill,skill is tools.

试想一个.mq.md文件，只需要撰写下来，智能体只需要每次执行：
```
marqdo call 文件名 函数名 函数参数
```
就能直接的得到执行结果，之后进行下一步的判断，更近一步，我们甚至可以在函数内写分支，但是让智能体决定走哪一个分支，让skill和tools不再强行分离。

甚至更近一步

```
marqdo call 文件名 函数名 函数参数 toget 返回值
```

得到返回值，在同一个会话进行多次的操作，之后记录下来，我们以后必定能够复现出来。

再进一步呢，智能体的输出就是marqdo脚本，只需要单步运行就能够得到结果。

## ABI插件

除此之外还有编程语言的特色，ABI插件，在deepseek harness中插件被证明是skill、mcp等的极好
接入方式，那么有没有可能marqdo可以实现每一个插件都是通过ABI接入的？

我想答案似乎是可以的。

这种情况下拓展库应该怎么设计呢？

我觉得应该按照模块设计

index.mq.md
    依赖1
        ……
    依赖2
        ……

其中index.mq.md就是这个拓展库的SKILL文档，AI只需要阅读这个文档就知道该怎么使用这个拓展库。

甚至更近一步的，index.mq.md本身就是一个可执行的文档，包含拓展库的全部功能。

## 叙述代码是否足够？

我想叙述性文字在AI编程中是非常重要的，所以，我在这里提出一个编程规范：

> 所有的函数叙述性文字必须和实际文字混合且超过50%

进行**校验**如果通过则**通过**否则**不通过**

这应该是我写的第一个SKILL即tools吧

所有的拓展库都要规划成为这样。

skill即tools有一个绝妙的地方那就是tools是函数，函数本身就对应一个操作，这个操作就是一个工具，所以每个skill都只需要调用本身就可以是tools了，同时marqdo的设计中包含有### 更深层的函数，这就是子工具了
